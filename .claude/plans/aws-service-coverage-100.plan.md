# Plan: Repeatable AWS Service Onboarding

**Source PRD**: `.claude/prds/aws-service-coverage-100.prd.md`
**Selected Milestone**: 1 — Onboarding cost is known
**Complexity**: Medium (small diffs; the measurement, not the code, is the deliverable)

## Summary

The service-onboarding pipeline already exists end to end — per-service model
download, a codegen scaffolder that writes a self-registering provider and
refuses to clobber a hand-written one, config that auto-enables every registered
service, and a main loop that needs no edit per service. Milestone 1 is therefore
a **repair-and-measure** job, not a build-a-tool job.

Two defects make the existing pipeline unusable and one makes its output dishonest:
the import generator gates on a file no service has, so it empties `imports.go`;
the scaffolded provider declines in a way that never reaches the CRUD engine, so
a new service serves zero operations; and the fidelity manifest would publish
those zero-op services as `auto-crud` anyway. Fixing all three is under 30 lines.
The remaining work is removing the one genuinely repetitive step (a hand-written
boto3 fixture per service — there are already 104) and then running the whole
path on one real service with a stopwatch.

## Tasks

### Task 1: Repair the import generator
- **Action**: Replace the `register.go` existence check with a check that the
  package actually registers a service (a `DefaultRegistry.Register(` occurrence
  in any `.go` file in the directory). After generation, exit non-zero if fewer
  services were written than a conservative floor — an empty or near-empty
  `imports.go` must fail loudly, never regenerate green.
- **Mirror**: `scripts/download-smithy-models.sh:79-88` — the closing block that
  exits non-zero with a comment naming the silent no-op it prevents.
- **Validate**: `bash scripts/generate-imports.sh && git diff --exit-code cmd/devcloud/imports.go`
  — the regenerated file must be byte-identical to what is committed today.
- **Watch**: the current header does not emit the SPDX line the committed file
  carries (`scripts/add-spdx-header.sh` adds it separately). Either emit it in
  the header or run the SPDX script after, or the idempotency check fails on a
  one-line diff.

### Task 2: Lock `imports.go` against drift
- **Action**: A Go test asserting every `internal/services/*` package that
  registers a service appears in `imports.go`, and vice versa.
- **Mirror**: `cmd/devcloud/conformance_test.go:24` — per-violation `t.Errorf`,
  a floor constant with a comment explaining the number.
- **Validate**: `go test ./cmd/devcloud/...`; delete one line from `imports.go`
  and confirm the test fails.

### Task 3: Make the scaffold meet the quality floor
- **Action**: In the scaffold template, return `plugin.ErrUnhandledOp` from
  `HandleRequest` instead of `generated.ErrNotImplemented`, and store
  `cfg.DataDir` in `Init`. This is what makes a new JSON-protocol service serve
  its CRUD-shaped operations the moment it is scaffolded.
- **Mirror**: `docs/crud-engine.md` — "a provider opts in by returning
  `plugin.ErrUnhandledOp` from its dispatch `default:` case".
- **Validate**: scaffold one service into a scratch directory, build, start the
  server, and confirm a `Create*` call returns 200 rather than an error.
- **Note (corrected during implementation)**: the engine's scope is narrower
  than "JSON-family". `crud.JSONProtocol` (`internal/shared/crud/crud.go:71`)
  matches only protocols starting with `json`, so **`rest-json` is out too**,
  not just Query / EC2 Query / REST-XML. Locally only 39 of 93 models (42%) are
  `awsJson1_0` / `awsJson1_1`; `rest-json` adds another 27 that a scaffold
  cannot serve. This shrinks Milestone 4's addressable set and is PRD Open
  Question 1 — **not** resolved here, see Open Decisions.

### Task 4: Stop the manifest overstating coverage
- **Action**: Extend the provider scan to record whether each service's dispatch
  returns `plugin.ErrUnhandledOp`. In `tierFor`, an operation is `auto-crud`
  only when its service is engine-wired; otherwise it stays `unimplemented`.
- **Mirror**: `gen_crud_meta.go` — classify only what can be established, skip
  rather than guess.
- **Validate**: `make codegen && git diff --stat` — expect **no change** to
  today's manifest, since all 46 JSON services are already wired. A non-empty
  diff means the wiring detection is wrong, not that the manifest was wrong.
- **Why it matters**: without this, Task 3's fix is unverifiable and every
  scaffolded service inflates the published coverage number.

### Task 5: Remove the per-service fixture cost
- **Action**: Add one parameterized boto3 client fixture built on the existing
  `_make_client`, plus a smoke test that, for each service under test, issues one
  request and asserts the service is routed and serves at least one operation.
  Leave the 104 existing named fixtures alone — they back real tests, not
  scaffolding, and rewriting them is out of scope.
- **Mirror**: `tests/compatibility/conftest.py:126` (`_make_client`) and the
  assertion style of `test_verifiedpermissions.py`.
- **Validate**: `make test-compat` — the existing 775 tests stay green and the
  new smoke test passes for at least one scaffolded service.
- **Watch**: the smoke test must fail for a service that routes but serves
  nothing. Confirm by pointing it at a service scaffolded *before* Task 3.

### Task 6: Measure the baseline — the actual deliverable
- **Action**: Take one JSON-protocol AWS service that is not currently
  registered, run the full repaired path with a stopwatch, and record each
  stage: model download, `make codegen` with `-scaffold-output`, import
  regeneration, build, smoke test, docs. Record wall-clock, lines of
  hand-written code, and anything that required a human decision. Write the
  number and the breakdown into the PRD's Success Metrics table.
- **Validate**: a second, different service reproduces the number within a
  reasonable margin. One data point is an anecdote.
- **Output**: the per-service cost figure that Milestone 2 sizes against and
  that Milestone 3 uses to decide whether 330 services is affordable.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Task 1 regenerates `imports.go` with a real diff (SPDX line, ordering), masking whether the fix is correct | High | Make byte-identical regeneration the explicit pass condition; resolve the SPDX gap before touching anything else |
| Task 3 makes 338 future services serve plausible-but-empty responses, accelerating the breadth-without-depth risk the PRD ranks first | High | This is the intended behaviour of the chosen quality floor, not a defect — Task 4 is the control that keeps the published number honest. Do not merge Task 3 without Task 4. |
| Task 4's wiring detection misclassifies a provider with an unusual dispatch shape, silently demoting live operations to `unimplemented` | Medium | The no-diff validation over today's 46 wired services is the check; any diff blocks the merge |
| The weekly sync workflow starts opening PRs again and immediately floods with scaffolded services | Medium | Verify what the repaired workflow produces before merging Task 1; the sync scaffolds from `smithy-models/`, which still holds only 93 models, so nothing new appears until models are added deliberately |
| The measured baseline is fast but unrepresentative — an easy service chosen first | Medium | Task 6 requires two services; prefer one small and one large rather than two small |
| Repairing the import generator surfaces that the weekly sync has been failing for a long time, with a backlog of upstream model drift | Medium | Expected. Land the repair first and review the resulting model diff as its own change, not inside this milestone |

## Open Decisions for the User

1. **Is the broken weekly sync in scope here, or its own fix?** Task 1 repairs
   the cause. Whatever upstream model drift accumulated while the job was failing
   is a separate, potentially large diff that should not ride along in this
   milestone.
2. **Which service is the measurement subject?** The plan needs one small and one
   larger JSON-protocol service not currently registered. `accessanalyzer` is a
   reasonable first candidate; confirm its protocol after download.
3. **Non-JSON protocols stay unresolved.** The scaffold fix only helps
   JSON-family services, so the quality floor remains unreachable for roughly 29%
   of the surface. That is PRD Open Question 1 and Milestone 5 — flagged here so
   it is not mistaken for something this milestone closes.
4. **Should the 104 hand-written fixtures be consolidated?** The plan says no —
   they back real tests and the parameterized fixture only serves new services.
   Say so if a consolidation pass is wanted instead.
