# Plan: Per-Operation Fidelity Manifest

**Source PRD**: `.claude/prds/aws-v1-stabilization.prd.md`
**Selected Milestone**: 1 — Fidelity manifest
**Complexity**: Large (1–2 days; Task 1 alone regenerates ~90 packages)

## Summary

Emit a generated, machine-verified manifest declaring every operation's fidelity tier (`hand-verified` / `auto-crud` / `unimplemented`), publish it as docs plus an admin API endpoint, and lock it with a test that fails if any operation is unclassified.

Three mechanical inputs already exist and only need joining: the Smithy models (universe), `crud.RegisteredOps()` (auto-crud), and the `case "OpName"` dispatch literals in each provider (hand-verified). Two prerequisites block a truthful manifest — the parser drops resource-attached operations, and two services carry no op-name literals at all.

## Findings That Shape the Plan

| Finding | Evidence | Consequence |
|---|---|---|
| Parser only walks `service.operations`, ignoring `resource` shapes — 285 operations invisible across 5 models (**bedrock 0 of 101**, lambda 19/85, ecs 12/76, transfer 29/71, sso-admin 67/79) | `internal/codegen/parser.go:112`; analysis over `smithy-models/*.json` | The op universe under-reports. `bedrock/provider.go:114` already carries the workaround comment *"since bedrock router is empty"*. Must fix first or the manifest's denominator lies. |
| 101 of 103 providers dispatch on op-name string literals | `grep -c 'case "'` per service | Hand-verified tier is mechanically extractable for nearly the whole surface. |
| **s3 and bedrock** route purely on method+path, zero op-name literals | `internal/services/s3/provider.go:89`, `internal/services/bedrock/provider.go:114` | These two need an explicit declared op list; everything else is derived. |
| 11 services have no Smithy model | `account cloudcontrol codeconnections dms identitystore mediaconvert pipes s3tables scheduler serverlessrepo verifiedpermissions` | Their `unimplemented` tail is not enumerable. Manifest must say so rather than imply full coverage. |
| `crud.RegisteredOps(service)` already exposes the auto-crud set | `internal/shared/crud/crud.go:62` | No new plumbing for tier 2. |
| Generated `OperationRoutes` is dead code — only referenced by a codegen test | `internal/codegen/gen_router_test.go:19` | Available to repurpose or delete; not load-bearing. |
| Admin API is a plain `http.ServeMux` with 3 routes | `internal/admin/api.go:33-35` | Adding `/devcloud/api/fidelity` is a few lines. |

## Tasks

### Task 1: Parse resource-attached operations
- **Action**: In `parser.go`, after collecting `service.operations`, walk each `resource` shape and append its `operations`, `collectionOperations`, and lifecycle targets (`create` / `read` / `update` / `delete` / `list`). Dedupe by shape FQN; keep the existing sort.
- **Mirror**: existing collection loop at `parser.go:112`, sorted for reproducibility.
- **Validate**: `go test ./internal/codegen/...`, then `make codegen && make build && make test && make test-compat`. Expect ~285 new ops; bedrock goes 0 → 101.
- **Watch**: regeneration adds new ops to the CRUD registry, so some operations that returned `InvalidAction` will start returning plausible auto-crud responses. That is a **behavior change** — review the `registry_gen.go` diff before accepting it, and decide whether bedrock's 101 newly-visible ops should be engine-wired at all.

### Task 2: Extract hand-verified operations
- **Action**: New codegen-side scanner using `go/parser` + `ast.Inspect`, scoped to the `HandleRequest` method body of each `internal/services/*` package: collect string literals from `case` clauses of the switch whose tag is the op variable. Ignore unrelated switches (e.g. `dynamodb/expression.go:527`).
- **Mirror**: `gen_crud_meta.go` classification style — skip what cannot be classified with confidence rather than guessing.
- **Override**: a small explicit map for `s3` and `bedrock` (path-routed, no literals), with a comment naming the ceiling and the upgrade path (declare ops next to the provider if the list grows).
- **Validate**: unit test asserting a known service resolves its known ops (e.g. `acm` includes `DescribeCertificate`, `sqs` includes `SendMessage`), and that `s3` / `bedrock` resolve from the override.

### Task 3: Generate the manifest
- **Action**: Join per service — universe (model ops, or `hand-verified ∪ auto-crud` when no model exists), `crud.RegisteredOps`, and the Task 2 set. Precedence is **hand-verified > auto-crud > unimplemented** (hand-written always wins, per `docs/crud-engine.md:37`). Emit `internal/generated/fidelity/manifest_gen.go` with counts per tier, a `ModelBacked bool` per service, and `Lookup(service, op) Tier`.
- **Mirror**: `GenerateCRUDRegistry` (`gen_crud_meta.go:145`) and the aggregate-file rationale in `registry_gen.go:5-7`.
- **Validate**: `make codegen` is idempotent — running twice leaves the tree clean (`git diff --exit-code`).

### Task 4: Lock it with a test
- **Action**: `manifest_test.go` asserts (a) every entry has a non-empty tier from the closed set, (b) every op in `crud.RegisteredOps` appears as `auto-crud` **or** `hand-verified`, (c) every override op exists in its service's universe, (d) a conservative floor on service and op counts.
- **Mirror**: `cmd/devcloud/conformance_test.go:24` — per-violation `t.Errorf`, floor constant with a comment.
- **Validate**: `go test ./internal/generated/fidelity/...`; deliberately corrupt one entry and confirm the test fails.

### Task 5: Publish
- **Action**: Add `GET /devcloud/api/fidelity` (optional `?service=`) returning the manifest as JSON. Write `docs/fidelity-manifest.md`; link it from `crud-engine.md` and `services-matrix.md`. Add the Changie entry.
- **Mirror**: `internal/admin/api.go:33-35` handler + `api_test.go` style.
- **Validate**: `go test ./internal/admin/...`; `make run` then `curl -s localhost:4747/devcloud/api/fidelity | head`.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| Task 1 silently widens auto-crud coverage — ops that honestly returned `InvalidAction` begin returning plausible responses | High | Review the `registry_gen.go` diff explicitly; decide per newly-exposed service whether engine-wiring is wanted before merging |
| Large regenerated diff hides a real break | Medium | Land Task 1 as its own commit gated on `make test-compat`; nothing else in the same commit |
| AST scanner misses a provider with a non-standard dispatch shape (beyond s3/bedrock) | Medium | Task 4's floor check plus a per-service assertion that any service with 0 hand-verified ops is on the override list — a new silent zero fails the build |
| Manifest asserts "100% classified" over an incomplete universe (11 model-less services) | Medium | Carry `ModelBacked: false` per service and state the limit in `docs/fidelity-manifest.md`; do not claim enumerable `unimplemented` where no model exists |
| Manifest drifts from code | Low | Generated only, never hand-edited; idempotency check in CI |

## Open Decisions for the User

1. **Task 1 in or out of this milestone?** It is the only thing standing between the manifest and a truthful denominator, but it is also the largest and riskiest diff. Splitting it out ships a manifest whose `unimplemented` counts are wrong for 5 services.
2. **Do newly-visible bedrock / lambda / ecs ops get engine-wired?** Fixing the parser makes them classifiable; whether they should be *served* is a separate call.
3. **Endpoint, docs, or both?** Plan assumes both (the admin mux makes the endpoint nearly free). Say so if docs-only is preferred.
